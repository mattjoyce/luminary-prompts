# Thompson × Feathers — trust × comprehension

*Pair review of the Luminaries repo at pre-release, read as a stranger arriving from a plugin marketplace. Axis: should you trust it (Thompson) held against can you comprehend and safely extend it (Feathers). One first-contact pass, two eyes kept separate. The adoption path simulated: land on `README.md` → read `.claude-plugin/{plugin.json,marketplace.json}` → `INDEX.md` → `skills/luminaries/SKILL.md` + `Workflows/` → sample a pair and a luminary. Severity: 🔴 must-fix · 🟠 should-fix · 🟡 consider.*

This is a benign artifact — a corpus of markdown prompts under CC0, no postinstall, no network calls, no code that runs unbidden. The blast radius is genuinely small, which is the good news and the frame for everything below: the trust question here is not "will it hurt me" but "can I account for what the installed skill instructs my agent to *do*, and can a newcomer touch it without silently breaking the routing that is its whole value." On both, the repo is close but ships with residue and unguarded seams.

## Thompson's findings — what must be taken on trust

**🔴 The three files the plugin actually executes carry a stray `</content>` tag — the one place residue is least acceptable.** `skills/luminaries/SKILL.md:111`, `skills/luminaries/Workflows/Review.md:46`, and `skills/luminaries/Workflows/Collate.md:47` each end with a bare `</content>` line that is not part of the document. This is the trust question in miniature: *whose hands has this passed through, and what did the chain leave behind?* An authoring tool wrapped these files in a `<content>` envelope and shipped the closing tag. It is harmless in effect, but it is unread residue in exactly the files a marketplace install feeds to an agent as instructions — the skill and its two workflows. A cautious adopter reading the skill to decide whether to trust it hits an artifact the author did not intend and cannot see. Delete all three lines.

**🟠 The install command cannot be verified from inside the repo, and the names don't obviously line up.** `README.md:142` says `/plugin marketplace add mattjoyce/luminary-prompts` and `plugin.json:8` gives `https://github.com/mattjoyce/luminary-prompts` — yet the working directory is `Luminaries`. Nothing a stranger can see confirms the GitHub repo is actually published at `mattjoyce/luminary-prompts`; if the repo ships under a different slug the very first command in the README fails. This is trust-in-reputation standing in for trust-in-artifact (lens Q4): the adopter takes the author's word that the remote exists and is named as claimed. Before release, verify the published repo slug matches the README and manifest exactly, or the front-door instruction breaks on line one.

**🟡 The skill instructs the agent to run shell on first invocation — read it, and confirm it's all it is.** `SKILL.md:25` has the agent execute `readlink -f`, `cd`, `pwd` to self-locate the repo. This is the "what runs that you haven't read" question, and to the repo's credit the answer is: read-only path resolution, nothing that reads secrets, writes outside, or phones home. Worth an explicit one-line assurance in the README's install section ("the skill runs only read-only path resolution; it makes no network calls and writes nothing outside a review folder you name") so the adopter doesn't have to reverse-engineer the blast radius themselves.

**🟡 `.gitignore:1–2` is itself a provenance tell.** The entry `${HOME}/` with the comment "Accidental literal-variable dir from an unexpanded `${HOME}` in some tool" is honest, and I credit the honesty — but it records that the toolchain around this repo has already once written a literal `${HOME}` directory the author didn't ask for. It is evidence the chain of hands is imperfect; it pairs with the `</content>` residue as the same class of signal. No fix needed beyond noting the pattern and scanning for other unintended artifacts before tagging.

## Feathers' findings — the seams, and whether a newcomer can change it safely

**🔴 There is no test, characterization or otherwise, that the routing table matches the files it routes to.** By Feathers' own definition this whole repo is legacy code — code (here, a routing table) without tests. The routing contract is duplicated by hand across at least five surfaces: the `INDEX.md:82–100` "All pairs at a glance" table (the actual routing table the skill reads), the categorized list at `INDEX.md:34–76`, the `README.md:19–37` pair table, the `README.md:104–133` roster, and `GROUNDINGS.md`. Every pair also must appear in both people's `pairs:` and `axis-roles:` frontmatter and their `## Pairings` section. Nothing *tells* you if these drift — only the author's word that they're in sync. The one characterization test worth writing: a script asserting every pair in the INDEX routing table has a `pairs/<slug>.md` that exists, every luminary link resolves, and every pair's two people back-reference it. Until that exists, a stranger changing anything is editing blind.

**🔴 `GROUNDINGS.md` is a derived artifact with no generator and no drift check.** It declares itself "concatenated… Canonical source is the individual files in `pairs/`" (`GROUNDINGS.md:3`), which correctly names `pairs/` as authoritative — but there is no script that regenerates it and no test that it still equals the concatenation. This is the classic README-rot seam Feathers warns of: edit a pair grounding, and `GROUNDINGS.md` silently diverges from the source it claims to mirror, and the adopter who "pastes the whole set at once" (README:75) gets stale lenses with no signal. Either generate it in CI or add a check that fails when it drifts.

**🟠 A newcomer can add a *luminary* by the book, but adding a *pair* — the higher-risk change — has no template and no documented procedure.** `luminaries/_TEMPLATE.md` is excellent: it carries per-section mode guidance and even a Naur acceptance test ("if only this file survived, could a capable model reconstruct the lens?"). But `pairs/` has **no** `_TEMPLATE.md` (confirmed: none exists), and no CONTRIBUTING doc or README section tells you the full ritual to add a pair — which touches the two routing tables, the README, `GROUNDINGS.md`, and both anchors' frontmatter. The asymmetry is backwards: the *safer* change (a person) is scaffolded; the *routing-breaking* change (a pair) is undocumented. Add a `pairs/_TEMPLATE.md` (Grounding + the pass structure, noting the Thompson×Feathers/Naur×Procida single/renamed-pass exceptions) and a short "Adding a pair" checklist enumerating every surface that must change.

**🟡 The observable seams for *using* the skill are good — credit where due.** The Subject/Stage/Intent classification (`SKILL.md:37–71`) is a clean enabling point: you can substitute a different routing decision without understanding the rest, and the selection examples (`SKILL.md:105–110`) let a newcomer observe expected behaviour without reading the whole. The fallback ("If you cannot resolve it programmatically, the repo root is the directory containing `INDEX.md`, `pairs/`, and `luminaries/`", SKILL.md:33) is a well-placed manual seam for when the shell resolution fails. This is the part a stranger *can* comprehend in one sitting.

**🟡 `readlink -f` is a portability seam that will bite on the author's own platform class.** `SKILL.md:25` depends on GNU `readlink -f`; on macOS/BSD `readlink -f` is absent or differs on older systems, and this repo lives on darwin. The documented-vs-actual gap Feathers hunts: the snippet *claims* to "self-locate… works wherever the repo is cloned," but its behaviour diverges by platform. The manual fallback covers it, so severity is low — but note the dependency, or use a portable resolution that doesn't assume GNU coreutils.

## Where the two eyes converge

Both lenses land, from opposite directions, on the same locus: **the files that constitute the shipped, executable surface — `SKILL.md` and the two workflows — carry unowned residue (`</content>`), and the routing they encode has no mechanism keeping it true.** Thompson reaches it asking "what runs here that no one has fully accounted for"; Feathers reaches it asking "what could I change here and not know I broke it." When the trust lens and the comprehension lens independently converge on *the same three files plus the routing table*, that is the highest-confidence signal in this review: the residue and the missing sync-check are the two must-fixes that gate release. Both are cheap. Both are the difference between "good" and "accountable."

## Where they pull apart — the tension for the owner

Thompson and Feathers disagree on **how much machinery this repo should carry, and the disagreement is real.**

Thompson's whole doctrine is that *simplicity is a trust strategy* — "the less there is, the more of it a person can actually account for" (thompson.md, tenet 4). From his eye, the repo's greatest trust asset is that it is *just markdown under CC0*: a stranger can read the entire blast radius in one sitting precisely because there is no build, no generator, no CI, no test harness to audit. Every piece of tooling Feathers wants to add (a link-checker, a GROUNDINGS generator, a drift test) is *itself new code that runs on the adopter's machine that they now have to trust* — new links in the chain, new unread execution. Thompson would say: fix the residue, verify the repo slug, and then *stop* — do not trade an auditable pile of text for an unauditable pipeline.

Feathers holds the opposite pole with equal right. To him a hand-maintained routing table duplicated across five surfaces with no test is *legacy code by definition* — the author's word is the only thing asserting it's correct, and "could a stranger change this safely today?" (feathers.md, The lens) is answered *no*. The corpus will grow (the INDEX already flags "new domain" pairs); every added pair widens the drift surface. Without a characterization test, comprehension rests on trusting the maintainer's diligence — the exact substitution Feathers refuses.

**The owner's decision, not to be averaged:** does Luminaries stay a *readable artifact* (Thompson — keep it all-text, keep the blast radius nil, accept that correctness is maintained by hand and hope) or become a *verified artifact* (Feathers — add the minimum tooling to make routing-correctness testable, accepting that the tooling is now something adopters must also trust)? The honest resolution is not the midpoint. It is to notice that Feathers' minimum viable check — a single read-only script asserting links and back-references resolve — costs Thompson almost nothing on the *adopter's* trust budget, because a linter that only reads files and is run by the maintainer never executes on the adopter's machine at all. That specific tool escapes the tension. Anything heavier (a generator the adopter runs, a CI the adopter must trust) lands squarely back in it, and there Thompson should win for a CC0 prompt corpus whose entire value proposition is legibility.
